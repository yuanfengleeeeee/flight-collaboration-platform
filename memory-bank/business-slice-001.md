# 业务切片 001：航班到达后的任务确认闭环

> 状态：业务设计已冻结，尚未开始代码实现
>
> 目标：减少“航班到达后已派任务，但组长仍需二次确认并电话通知员工”的重复沟通。

## 用户价值

航班到达事件产生后，系统依据班组、岗位能力和人员状态生成候选人；班组长确认后，系统在站内任务中通知唯一员工，员工接收并完成任务。第一版不接入 AI、不接入真实短信/企业微信，也不依赖定位硬件。

## 范围

- 使用一个人工录入或测试触发的航班到达事件。
- 为该事件生成一个已配置的保障任务实例，保存任务模板版本。
- 按硬约束筛选候选员工：属于任务班组、具备所需岗位/能力、当前状态为空闲。
- 候选排序采用确定性规则：最近状态更新时间较早者优先，同值按员工 ID 升序；不引入预测模型。
- 班组长逐任务确认唯一候选人；第一版不做批量确认。
- 确认后创建站内通知记录；员工可以查看、接收、完成任务。
- 全过程记录操作人、时间和状态变化。

## 不在范围内

- 自动调度、自动替代班组长确认、多人抢单。
- 位置区域作为第一版硬约束；位置字段保留为后续筛选条件。
- 真实推送渠道、RFID/UWB、AI 风险预测。
- 航班取消、登机口变更、复杂任务模板编排和跨航班调度。
- 管理端完整的班组/岗位/人员 CRUD；第一版使用迁移后的测试夹具或最小内部接口提供基础数据。

## 触发与幂等

- 事件类型固定为 `flight_arrived`。
- 每次事件必须有 `source_event_id`；重复提交同一来源事件不得重复生成任务。
- 没有外部来源 ID 的测试事件使用 `flight_id + event_type + occurrence_date` 作为幂等键。
- 一个幂等事件最多生成一个目标任务实例；任务模板版本必须写入任务实例。

## 状态机

任务实例：

```text
pending → awaiting_confirmation → assigned → in_progress → completed
                 │                    │          │
                 └────────────────────┴──────────┴→ cancelled/expired
```

分配记录：

```text
proposed → confirmed → accepted → completed
     └──────────────→ rejected
```

约束：

- 只有班组长或管理员可以将 `proposed` 改为 `confirmed`。
- `confirmed` 后才允许通知员工。
- 一个任务实例只能有一个有效分配记录；员工不能自行把任务分配给其他人。
- 员工只能接收分配给自己的任务；完成前必须处于 `accepted` 或 `in_progress`。
- 所有非法状态转换返回稳定错误码并写审计记录。

## 权限与数据范围

- 管理员：可查看和维护本切片基础数据，拥有应急处理权限。
- 值班经理：可查看航班、任务和运行状态，但第一版不替代班组长确认。
- 班组长：只能查看负责班组和航班范围，可确认/拒绝候选分配。
- 一线员工：只能查看、接收和完成分配给自己的任务。
- 第一版先实现角色权限和班组 ID 数据范围；跨班组查询默认拒绝。

## 验收标准

1. 同一到达事件重复提交时只存在一个任务实例。
2. 候选列表排除非本班组、无所需能力和非空闲员工。
3. 班组长确认前，员工收不到可执行通知；确认后才生成一条站内通知。
4. 同一任务不能被两名员工接收；并发接收只有一个成功。
5. 员工只能操作自己的任务，完成任务后任务和人员状态正确更新。
6. 组长确认、员工接收、员工完成均可追溯到操作人和时间。
7. 失败、重复、越权和非法状态转换都有稳定 HTTP 错误响应和测试覆盖。
